📓 Cassandra Quick-Revise Notes

A fast-reference cheat sheet: what Cassandra is, when to pick it, how it works, and how it differs from Postgres.

1 · What is Cassandra?

Apache Cassandra is a distributed, leaderless (masterless) NoSQL database that is highly available and fault-tolerant. It was originally created at Facebook (by an Indian engineer, Avinash Lakshman, along with Prashant Malik) and later open-sourced. It is designed to run across many commodity servers with no single point of failure.

  • Type: Wide-column / NoSQL store, speaks CQL (Cassandra Query Language).
  • CAP classification: AP by default (Availability + Partition tolerance), with tunable consistency per request.
  • Throughput: can sustain 100k+ writes/sec on a modest cluster — built for write-heavy, append-mostly workloads.
  • Model: "Partition-first" — every query is designed around a partition key; rows inside a partition are ordered by clustering columns.
One-liner to remember: "A masterless, write-optimized, horizontally scalable key-value/wide-column store that trades query flexibility for availability and scale."

2 · When should you choose Cassandra? USE

  • Write-heavy workloads — e.g. event logs, telemetry, IoT sensor data, activity feeds, time-series (Cassandra is famous for its append path).
  • Global scale with multi-datacenter replication — data must be available in several regions with low write latency.
  • High availability / no downtime — you can accept slightly stale reads but cannot accept a down database; rolling upgrades, node loss should not stop writes.
  • Availability > consistency — the CAP choice Cassandra fits (AP by default).
  • High write throughput — LSM storage makes Cassandra an especially good fit for write-heavy systems.
  • Flexible / sparse schemas — wide columns that vary per row.
  • Data is mostly keyed by a natural partition — e.g. "give me all of user_id's events", "all readings for sensor_id".
  • Horizontal scale-out — adding nodes = adding capacity linearly, with automatic rebalancing (consistent hashing).
  • A few clear access patterns you can model tables around.
Sweet spot: "Append-heavy, key-based access, always-on, scale-out."

3 · When should you avoid it? AVOID

  • Strict consistency required — Cassandra is heavily biased toward availability, so strong-consistency systems fit poorly.
  • Ad-hoc / complex queries — no JOINs, no GROUP BY over the whole table, no arbitrary WHERE on non-key columns. You must model tables per query pattern upfront.
  • Relational integrity — no foreign keys, no ACID transactions across multiple rows/partitions (only single-partition "lightweight transactions").
  • Strong consistency / reads-must-be-current — eventual consistency is the norm; cross-partition strong consistency is not a thing.
  • Frequent updates & relational joins — Cassandra is great for append-heavy, not for normalized OLTP with heavy joins.
  • Aggregations / analytics on big scans — a data warehouse (Postgres columnar, ClickHouse, BigQuery) is better for analytics.
  • Small data, single node — if you just need one machine with SQL, Postgres is simpler and more powerful.
  • Transactions spanning entities — e.g. bank transfers (debit + credit together) are painful; a relational DB with ACID is the natural fit.
Red flag: If you can't describe your access pattern with "partition key + clustering order", Cassandra will fight you.

4 · How does it work?

a) Data distribution — consistent hashing

  • The partition key is hashed (Murmur3) to a token on a ring (range 0…2^127).
  • Every node owns a token range; the row is stored on the node(s) that own the token of its partition key.
  • Adding a node splits ranges → automatic rebalancing, no manual sharding.

b) Replication & fault tolerance

  • Each partition is replicated to RF (replication factor) nodes (e.g. RF=3 → 3 copies).
  • SimpleStrategy = single DC; NetworkTopologyStrategy = multi-DC (preferred in production).
  • Gossip protocol lets nodes learn about each other's state — no central coordinator, the cluster is self-healing.
  • If a node dies, other replicas still serve reads/writes; hinted handoff & repairs restore consistency later.

c) Tunable consistency

  • Per-request ConsistencyLevel: ONE, QUORUM, ALL, LOCAL_QUORUM, etc.
  • QUORUM = majority of replicas (RF/2 + 1) must ack → balances correctness & latency.
  • Write path: commit log → memtable → SSTable (on flush). Reads may hit multiple replicas + read repair.

d) Partition + clustering (the key mental model)

CREATE TABLE sensor_readings ( sensor_id text, -- PARTITION key timestamp timestamp, -- CLUSTERING key id text, temperature double, humidity double, PRIMARY KEY ((sensor_id), timestamp, id) -- ( (partition), clustering... ) ) WITH CLUSTERING ORDER BY (timestamp DESC);
  • All rows with the same sensor_id live in one partition (co-located on the same nodes).
  • Inside a partition, rows are physically sorted by clustering columns — so ORDER BY is a schema-time decision, not query-time.
  • Queries must always filter by the partition key; range/order only along the clustering columns.
  • Primary key types: PRIMARY KEY (a) · PRIMARY KEY ((a), b) (a = partition, b = cluster) · PRIMARY KEY ((a, b), c) (composite partition) · PRIMARY KEY ((a), b, c) (multi clustering). Same idea as DynamoDB's key design.

e) Query routing (leaderless / coordinator)

  • Any node can serve any query — the client picks a node, that node becomes the coordinator and routes to the replicas that hold the data.
  • Nodes learn the full cluster layout via gossip (no central metadata server, no single point of failure).

f) Gossip & fault tolerance

  • Gossip: nodes periodically exchange cluster state (alive/dead, schema) with random peers, biased toward seed nodes (guaranteed "hotspots"). Generation + version numbers form a vector clock so stale gossip is ignored.
  • Failure detection: Phi Accrual Failure Detector — a node "convicts" a peer that stops heartbeating and stops routing writes to it. Convicted nodes stay in the ring (no instant re-balance).
  • Hinted handoff: if a write target is down, the coordinator stores a hint and replays it when the node returns — short-term protection against data loss.

g) Consistency levels & the CAP trade-off

  • Per-request ConsistencyLevel: ONE, QUORUM, ALL, LOCAL_QUORUM, etc.
  • QUORUM (majority = RF/2 + 1) on both read & write guarantees the read sees the write (at least one node overlaps).
  • No ACID/transactions — only atomic, isolated single-partition writes (row-level in a partition). Eventual consistency is the norm.
  • For every request you tune the triangle: consistency vs correctness vs uptime.

5 · Storage model — why writes are so fast (LSM tree)

Cassandra uses a Log-Structured Merge (LSM) tree instead of a B-tree. It optimizes for write speed over read speed: every create/update/delete is basically an append. Deletes write a tombstone.

  • Commit Log — write-ahead log for durability (writes survive a crash).
  • Memtable — in-memory, sorted-by-primary-key structure holding recent writes.
  • SSTable — immutable file on disk, produced when a Memtable is flushed (on size/time threshold).
write → commit log → memtable → (flush) → SSTable → compaction
  • Reads: memtable first (latest), then bloom filter to pick candidate SSTables, read newest → oldest.
  • Compaction merges SSTables into a consolidated set, removes tombstones/deleted rows.
  • SSTable index maps keys → byte offsets for fast on-disk lookup.

6 · Data modeling — query-driven, not entity-driven

Relational modeling is entity-driven (normalize, JOIN via FKs). Cassandra is query-driven: no JOINs, no FKs, no flexible queries — so you model tables around the access patterns and denormalize data across tables.

Decide per table

  • Partition key — what data determines the partition.
  • Partition size — can a partition grow unbounded? (Large partitions = slow.)
  • Clustering key — how rows should be sorted.
  • Denormalization — duplicate data into per-query tables.

Example: Discord messages

-- v1: one partition per channel CREATE TABLE messages ( channel_id bigint, message_id bigint, author_id bigint, content text, PRIMARY KEY (channel_id, message_id) ) WITH CLUSTERING ORDER BY (message_id DESC);
  • message_id is a Snowflake ID — chronologically sortable, no collision (timestamp would collide).
  • Problem: busy channels → huge partitions that grow forever → slow.
  • Fix: add a bucket (10 days) to the partition key:
PRIMARY KEY ((channel_id, bucket), message_id) -- bounded partition size

Example: Ticketmaster tickets

-- v1: one partition per event PRIMARY KEY (event_id, seat_id) -- 10k+ seats → big partition -- v2: partition by (event, section) — smaller partitions, matches UI clicks PRIMARY KEY ((event_id, section_id), seat_id) -- separate denormalized table for the venue overview CREATE TABLE event_sections (event_id bigint, section_id bigint, num_tickets bigint, price_floor bigint, PRIMARY KEY (event_id, section_id));
  • UX drives schema: users click a section → query that partition.
  • Top-level overview is served by a denormalized event_sections table (approximate counts are fine — eventual consistency is acceptable).
Takeaway: "Design the table for the query, bound the partition size, denormalize for reads."

7 · Cassandra vs PostgreSQL

AspectPostgreSQLCassandra
TypeRelational (SQL), ACIDWide-column NoSQL, CQL
CAPCP (consistency first)AP by default (tunable)
Joins / relationshipsFull SQL: JOINs, FKs, subqueriesNo JOINs, no FKs
Query modelFlexible — any column, any timeMust be designed per query (partition key first)
TransactionsACID, multi-row, multi-tableOnly single-partition (LWT), no cross-partition ACID
ConsistencyStrong by defaultEventual, tunable per request
ScalingVertical first; read replicas; harder to scale writesHorizontal by design — add nodes, automatic rebalancing
Write throughputGood, but bounded by single primaryVery high (100k+ writes/sec/cluster)
OrderingORDER BY at query timeClustering order at schema time
Best forTransactions, relational data, analytics, correctnessWrite-heavy, always-on, key-based access at scale
Rule of thumb: Need joins/transactions/flexible queries → Postgres. Need massive write scale, multi-DC availability, key-based access → Cassandra.

8 · Advanced features (nice to know)

  • Storage-Attached Indexes (SAI) — global secondary indexes on columns; lets you query non-key columns with decent performance (worse than partition-key queries). Avoids over-denormalizing for rare queries.
  • Materialized Views — Cassandra auto-maintains a denormalized table from a source table, so your app doesn't have to write to multiple tables.
  • Search indexing — wire Cassandra to Elasticsearch/Solr (e.g. Stratio Lucene Index) for full-text search.

9 · Blog Summary — "Cassandra Deep Dive" BLOG

📄 Summarized from a Cassandra deep-dive study guide (PDF) covering how Cassandra works, when to use it, and real-world data-modeling examples.

Origin & fit

  • Built by Facebook (originally for inbox search), now open source; used by Discord, Netflix, Apple, Bloomberg.
  • Open-source, distributed NoSQL, partitioned wide-column store, eventually consistent; combines ideas from Dynamo (partitioning/availability) and Bigtable (storage model).
  • Horizontally scales on commodity hardware.

Data model

  • Keyspace ≈ a "database" (defines replication); Table, Row, Column (wide-column — columns can vary per row; each column carries write timestamp metadata; conflicts resolve by last-write-wins).
  • Think of it like a giant JSON: keyspace → table → row → column.

Core internals (the interview "points")

  • Consistent hashing on a ring with vnodes (virtual nodes) → even load, minimal remapping on node add/remove.
  • Replication: scan clockwise for RF replicas (skip same-physical-node); NetworkTopologyStrategy (production, DC/rack aware) vs SimpleStrategy.
  • Consistency levels (ONE…ALL); QUORUM read+write guarantees the write is visible to the read.
  • Query routing: any node = coordinator (leaderless).
  • LSM storage (commit log → memtable → SSTable → compaction) = fast appends.
  • Gossip + Phi Accrual Failure Detector + hinted handoff = self-healing, fault-tolerant.

Interview verdict

  • ✔ Use when: availability > consistency, high write throughput, flexible/sparse schemas, and a few clear access patterns to model around.
  • ✘ Avoid when: strict consistency, multi-table JOINs, ad-hoc aggregations needed.
