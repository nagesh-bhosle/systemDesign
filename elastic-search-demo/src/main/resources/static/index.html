📚 System Design Interview Notes — Elasticsearch

Scannable, bullet-heavy reference for the whiteboard. No fetch — pure static HTML.

Why ES Postgres vs Elasticsearch

  • LIKE '%q%' is O(n) scan — no index, no ranking.
  • tsvector / tsquery helps but limited: basic ranking, no fuzzy, weak geo, no aggregations.
  • ES gives inverted index + BM25 + analyzers + geo BKD + aggs in one engine.
  • Trade-off: eventual consistency (refresh 1 s), extra infra, dual-write complexity.
  • Rule of thumb: PG for transactional truth; ES for search, discovery, analytics.

Core Document → Index → Shard → Segment

  • Document = JSON row · Index = collection/table · Shard = partition (primary + replicas).
  • Segment = immutable Lucene file with its own inverted index; background merge compacts them.
  • Inverted index: term → sorted doc IDs + positions + frequencies.
  • Analyzer chain: char filter → tokenizer → token filters (lowercase, stemmer, stop, synonym).
  • Mapping types: text (analyzed), keyword (exact), geo_point, numeric, date.

Write Indexing path

  • Client → bulk index → primary shard → replica shards (async/sync).
  • In-memory buffer → refresh (1 s) → new segment visible for search (near-real-time).
  • Translog (WAL) → fsync for durability; on crash replay translog.
  • Background segment merge reduces segment count, reclaims deletes.
  • Tuning: increase refresh_interval for bulk loads; use bulk not single docs.

Read Search path

  • Scatter: coordinator fans query to all shards (or routing shard).
  • Gather: each shard scores locally (BM25), returns top-k doc IDs + scores.
  • Coordinator merges, re-sorts, fetches stored fields — then highlight / aggs / sort.
  • BM25: TF × IDF × field-length norm — rewards rare terms, penalizes long fields.
  • Pagination: from/size for shallow, search_after / scroll for deep.

🌍 Geo

  • geo_point indexed in BKD tree — 2-D numeric range tree, very fast radius.
  • Queries: geo_distance (within X m), geo_bounding_box, geo_polygon.
  • Sort: _geo_distance — returns distance per hit for display.
  • Aggregations: geohash_grid / geo_distance buckets for heatmaps.
  • PG PostGIS ST_DWithin is fine for low QPS; ES geo wins at high concurrency.

⭐ Relevance

  • BM25 default — tuned via k1 (TF saturation) and b (length norm).
  • Boosting: multi_match: { fields: ["name^3","description"] } — name hits ×3.
  • Function score: decay on distance/recency, boost on rating/popularity.
  • Highlighting: per-field snippets with <em> tags, cheap at query time.
  • Synonyms & analyzers: english stemmer, custom filters for domain jargon.

⌨️ Autocomplete

  • edge_ngram: index prefixes (p, pi, piz, pizz…) — simple, supports typo via fuzzy.
  • completion suggester: FST in memory — fastest, but exact prefix, separate data structure.
  • search_as_you_type: built-in n-grams + shingle — best balance, supports slop.
  • This demo: /api/suggest backed by ES completion/edge_ngram — debounced 200 ms on client.
  • Keyboard nav: ArrowUp/Down + Enter + Esc; blur hides after 150 ms.

⚖️ When to pick ES vs PG

  • Pick PG: strong consistency, joins, transactions, low search volume.
  • Pick ES: full-text, fuzzy, geo, facets/aggs, high QPS search.
  • Both: PG as source of truth, ES as derived read model — dual-write problem.
  • Sync: outbox pattern → CDC (Debezium) → Kafka → ES indexer (at-least-once, idempotent).
  • Failure modes: lag, drift, split-brain — reconcile via periodic batch reindex / checksum jobs.
  • Scaling: more shards = write parallelism; more replicas = read parallelism & HA. Avoid oversharding.

🧩 Mapping & Query DSL — copy-paste starters

Mapping (index creation)
{ "mappings": { "properties": { "name": { "type": "text", "analyzer": "english", "fields": { "keyword": { "type": "keyword" } } }, "description": { "type": "text", "analyzer": "english" }, "category": { "type": "keyword" }, "location": { "type": "geo_point" }, "avgRating": { "type": "float" }, "suggest": { "type": "completion" } } } }
Query DSL (combined text + geo + filter)
{ "query": { "bool": { "must": [ { "multi_match": { "query": "spicy pizza", "fields": ["name^3", "description"], "fuzziness": "AUTO" }} ], "filter": [ { "term": { "category": "restaurant" }}, { "geo_distance": { "distance": "1km", "location": { "lat": 37.7749, "lon": -122.4194 } }} ] } }, "sort": [ { "_geo_distance": { "location": [-122.4194, 37.7749], "order": "asc", "unit": "m" }} ] }
▸ More: scaling & failure checklist
  • Shard count is fixed at index creation — reindex to change; prefer 1 shard per ~30 GB.
  • Replicas add HA but double indexing cost; set index.number_of_replicas: 1 minimum in prod.
  • Hot/warm architecture: recent indices on SSD, older on HDD; ILM for rollover.
  • Circuit breaker & queue rejections under heap pressure — monitor _cat/thread_pool.
  • Snapshot to S3/GCS; test restore drills — ES snapshots are incremental and cheap.
